# kz-support-lora: дообучение модели для tool calling в поддержке на казахском и русском

Дата: 2026-10-29, обновлено после обсуждения плана в тот же день. Решения принимал Нурмухамед; где решение предложил Claude и оно принято без обсуждения, это помечено «(решение Claude)».

## Зачем

Нурмухамед переходит из AI-инженерии (LLM через API, RAG, агенты) в ML-инженерию (LLM). Главная дыра в профиле, по вакансиям в Алматы и по пробному ML-собеседованию: он сам ни разу не дообучал модель и не мерил результат. Целевые вакансии: Kaspi ML Engineer в команде агентных систем (PEFT/LoRA, SFT, оценка качества, LLM в проде) и NLP-роли в Алматы.

Проект должен дать:
- строку в резюме вида «дообучил модель через LoRA: метрика X → Y», с честными цифрами;
- материал для собеседования: решения, ошибки, trade-off'ы, которые он защищает сам;
- публичные артефакты, которые интервьюер открывает по ссылке.

Почему эта задача: в Казахстане клиенты пишут в поддержку на смеси казахского и русского и часто пишут **казахские слова русскими буквами** без ә, қ, ғ, ү, ұ, і, ө, ң, һ («Салем, заказым али келмеди»). Большие модели и токенизаторы на этом спотыкаются. Это реальная боль поддержки интернет-магазинов и аптек, близкая к задачам Kaspi.

Формат — сильный пет-проект. Реальный прод у заказчика отпал: заказчик вряд ли даст переписку клиентов.

## Как работаем

- Код генерации данных, обучения и оценки **пишет Нурмухамед руками**. Claude не пишет код за него.
- Ревью: Нурмухамед делает шаг, коммитит и пишет «ревью». Claude читает diff и отвечает по приоритету: (1) то, что ломает цифры — утечка теста, неверная метрика, баг нормализации; (2) обычные баги; (3) оптимизации и улучшения. Объясняет, что не так и почему, но не правит.
- Причина: на собеседовании он должен защитить каждую строку (совет Динмухамеда — не вайбкодить, понимать, что под капотом).

## Порядок работы

Сначала оценка, потом обучение:

2. нормализация и метрики в `.py` с тестами;

## Задача

Один ход. На вход — одно сообщение клиента и **контекст: 0–3 последних заказа пользователя** в JSON в системном промпте. На выход — один вызов инструмента. Реальный чат поддержки внутри приложения знает, кто пишет, поэтому номер заказа клиент обычно не пишет («ГДЕ МОЙ ЗАКАЗ???») — модель находит нужный заказ в контексте.

Пример:

```
Контекст: заказы пользователя
  #48213 — Наушники JBL, доставлен вчера, Алматы
  #51002 — Терафлю ×2, в пути, Алматы

Сообщение: «Наушниктер бузык келди кайтарам»
→ request_return(order_id="48213", product="наушники jbl")
```

Поля заказа в контексте: номер, товары, статус (оформлен / в пути / доставлен / отменён), дата, город. Пустой контекст допустим (например, вопрос о наличии лекарства).

Почему один ход: у одного сообщения ровно один правильный вызов, exact match считается однозначно. Диалог требует симулятора клиента или LLM-судьи, честную оценку за 1–2 недели не построить.

### Инструменты (11)

| Инструмент | Когда |
|---|---|
| `get_order_status()` | Где заказ. Без аргументов — статус всех активных заказов (уточнять не нужно) |
| `cancel_order(order_id)` | Отменить заказ до получения |
| `request_return(order_id, product)` | Вернуть товар после получения |
| `report_payment_issue(order_id?, issue)` | Двойное списание, оплата не прошла, деньги не вернули |
| `change_delivery_address(order_id, new_address)` | Сменить адрес доставки |
| `check_product_availability(product)` | Есть ли товар (магазин возит по всей стране, город не нужен) |
| `check_prescription_required(drug)` | Нужен ли рецепт |
| `find_drug_analog(drug)` | Аналог лекарства |
| `check_drug_stock(drug, city)` | Есть ли лекарство в аптеках города |
| `ask_clarification(missing)` | Действие понятно, но неясно, какой заказ / не хватает данных |
| `escalate_to_human(reason)` | Жалоба или вопрос не по теме |

Ключевые места, где модель должна ошибаться и учиться: отмена vs возврат (получен ли товар), товар vs лекарство, «хватает данных» vs уточнение, сопоставление фразы с нужным заказом в контексте.

### Схема аргументов

- Enum: `city` (17 областных центров + 3 города республиканского значения + `"other"`), `issue`, `reason`, `missing`. Модель приводит «Алматыда», «Астанаға», «Almaty», «Алмата» к каноническому названию.
- Строки: `product`, `drug` — модель возвращает начальную форму («парацетамол», а не «парацетамолды»). Сравнение после нормализации: нижний регистр, казахские буквы → русские.
- `order_id` — строго из контекста.
- Необязательный аргумент остаётся только там, где его отсутствие имеет свой смысл, иначе exact match получает два «правильных» ответа (решение Нурмухамеда, 2026-10-29):
  - `get_order_status` без аргументов — всегда статус всех активных заказов;
  - `report_payment_issue`: `order_id` пуст, только когда заказа нет (оплата не прошла и заказ не создался); заказ есть, но неясно какой → `ask_clarification(missing="order_id")`;
  - `request_return`: `product` обязателен — один товар в заказе берётся из контекста, несколько и неясно какой → `ask_clarification`;
  - `check_product_availability`: `city` убран.
- Свободный текст (`new_address`) в exact match не входит, проверяется отдельно: заполнен или пуст.

### Стили письма (5)

Правильный казахский; казахский русскими буквами; смесь казахского и русского; русский; латиница (транслит). Все метрики качества считаются и отдельно по каждому стилю.

### Формат вывода

Родной шаблон tool calling каждой модели: Hermes-стиль `<tool_call>` у Qwen, шаблон Llama 3.1 у KazLLM. vLLM отдаёт вызовы наружу в OpenAI-формате; скрипт оценки приводит ответ к `{"name", "arguments"}`.

## Данные

Все наборы строятся по **карточкам**: скрипт генерирует контекст заказов, ситуацию («наушники пришли сломанные, хочешь вернуть», «не знаешь, где заказ, нервничаешь») и стиль. Правильный вызов известен из карточки — ручная разметка почти не нужна, баланс по инструментам и стилям получается автоматически. Ситуация на карточке — описание, а не готовая фраза.

| Набор | Откуда | Размер | Роль |
|---|---|---|---|
| Обучающий | Claude через подписку Pro (`claude -p`, батчами ~50 за вызов) пишет сообщения по карточкам + автоматическая замена казахских букв на русские (ә→а, қ→к, ғ→г, ү/ұ→у, і→и, ө→о, ң→н, һ→х) для части примеров на правильном казахском | ~4000 (11 инструментов × 5 стилей × ~70) | обучение |
| Валидационный | 5–10% от обучающего | пара сотен | выбор чекпойнта и гиперпараметров |
| Тест живой (главный) | Нурмухамед ~150 сообщений, 2 друга ~по 25, по карточкам | 200 | только финальный замер |
| Тест синтетический (доп.) | Gemini (бесплатный API Google AI Studio) по карточкам; Нурмухамед проверяет глазами | ~300 | проверка, не подстроилась ли модель под стиль Claude |

Состав живого теста: 40 сообщений на стиль; каждый инструмент минимум 10 раз; ~20% — уточнение (неясно, какой заказ); ~10% — жалобы и вопросы вне темы.

Проверка обучающих данных:
- автоматика: в стиле «казахский русскими буквами» нет ни одной ә/қ/ғ/ү/ұ/і/ө/ң/һ, в «правильном казахском» они есть; сообщение не повторяет текст карточки;
- дубли: точное совпадение после нормализации (регистр, пунктуация, буквы) + похожесть строк через `rapidfuzz` (> 90%). Скрипт сохраняет **отчёт со всеми найденными парами и их похожестью**; Нурмухамед просматривает его и решает сам. Той же проверкой считается, сколько живых тестовых сообщений почти совпадает с обучающими, — цифра идёт в README;
- выборочный просмотр 100 случайных примеров глазами, доля плохих — в README.

Правила:
- Тесты не попадают в обучение и не используются для подбора гиперпараметров.
- В живом тесте казахский русскими буквами только живой, без автоматической замены.
- Чужие персональные данные не используются; данные с сайтов не собираются.
- Сообщения друзей публикуются только с их согласия.
- В карточке модели указано, кто и сколько писал тест.

Обучающие данные от Claude — решение Нурмухамеда: проект учебный, маленькая модель, конкуренции с Anthropic нет. По сути это **дистилляция «учитель → ученик»**, в README и посте её так и называем. Генерацию запускаем рано (около 3-го дня): ~100 вызовов растягиваются на несколько окон лимита Pro.

| Модель | Роль |
|---|---|

| Qwen3-1.7B | насколько можно уменьшить, LoRA |

## Обучение

- SFT через TRL `SFTTrainer` + PEFT, QLoRA (4 бита).
- **Loss только по ответу модели** (токены вызова), не по промпту, контексту и сообщению.
- Ранг LoRA, learning rate и прочее подбираются на валидации, отдельным экспериментом не оформляются.
- Железо: бесплатные Google Colab (T4 16 ГБ) и Kaggle (~30 ч GPU в неделю). Сессии обрываются: чекпойнты на Google Диск / Hugging Face Hub, обучение продолжается с чекпойнта. Домашний ПК с RTX 3060 12 ГБ сейчас недоступен (SSH удалён); если доступ вернётся — бонус.
- MacBook (16 ГБ): код, генерация данных, оценка, демо.
- Логи экспериментов — **MLflow**: `mlruns` на Google Диске, интерфейс `mlflow ui` локально на Mac. На Kaggle — та же папка через Kaggle Dataset или ручная выгрузка.

## Эксперименты

Главный прогон: LoRA на Qwen3-4B. Вокруг него:
1. **С заменой букв и без** — помогает ли искусственный «казахский русскими буквами» понимать живой.
2. **Кривая по объёму данных**: 500 / 1000 / 2000 / 4000 примеров.
3. **Constrained decoding** (vLLM, xgrammar) с ним и без — что даёт гарантированно валидный JSON и что не даёт (выбор инструмента и аргументов он не улучшает).

## Метрики

Качество (весь тест и по каждому стилю):
- **Exact match** — главная: верны инструмент и все однозначные аргументы после нормализации. Идёт в резюме.
- Точность выбора инструмента.
- F1 по аргументам (частичный зачёт).
- Macro-F1 по инструментам.
- Доля валидного вызова по схеме.
- Доля выдуманных аргументов: значения нет ни в сообщении, ни в контексте, а модель его вписала вместо `ask_clarification`.

Эксплуатация:
- задержка p50 / p95 на запрос: своя модель через vLLM на T4 против Claude;
- цена за 1000 запросов: Claude — по публичной цене API за токены (подписка цену не показывает), своя модель — по цене часа аренды аналогичного GPU; с расшифровкой.

Надёжность: bootstrap-интервал к каждой метрике качества. Прирост меньше погрешности (при 200 примерах и точности ~80% — около ±6 п.п.) называется шумом.

## Не цели (первая версия)

- Классификатор диалектов.
- Обучение с нуля.
- Диалог в несколько ходов и память.

## Анти-цели (провал, даже если всё работает)

- Цифры, которые нельзя защитить: тест утёк в обучение, тест сгенерирован той же моделью, что и обучающие данные, прирост в пределах шума выдан за улучшение, метрика посчитана непротестированным кодом.
- Нурмухамед не может объяснить на собеседовании, что и почему сделано в коде. Код написан за него.
- Использованы чужие персональные данные или данные, собранные в обход правил сайтов.
- Проект подаётся как «прод», хотя это пет-проект.
